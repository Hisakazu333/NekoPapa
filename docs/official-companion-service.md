# 官方人物与 Java 服务的边界

更新日期：2026-11-22。

官方人物的人设提示词由 NekoPapa 的 Java 后端维护和执行。桌面端的人物目录只提供 ID、姓名、简介和外观资源，简介不是用于拼装人设的提示词。用户只能查看官方人物资料，并使用单人陪伴聊天和学习模式；不能修改、复制其提示词，也不能把官方人物加入群聊。

自建联系人保留用户配置的提示词，可用于专业事务和自建联系人群聊。选择与官方人物相同的外观不会获得官方人物身份或其后端人设。

## 当前实现

- `src/app/contacts/companion-catalog.ts`提供五位官方人物的公开展示资料；稳定 ID 保持 `lumia`、`rinne`、`iori`、`shiori`、`tsumugi`。
- `src/app/api/chat/contact-prompt.ts` 只组装普通工作台和自建联系人的通用模型提示词。官方人物资料不能传入该函数生成本地人设。
- `/api/chat` 的 GET 响应单独提供 `officialCompanions.configured` 与 `reason`，区别于通用模型的 `configured`。当前官方人物服务为未接入，即使开发服务器已经配置模型密钥也不会变为可用。
- 官方人物 POST 请求先检查身份、客户端系统消息和群聊限制；合法的单人请求当前返回 `503 official_companion_unavailable`。不会向通用模型发送公开简介，也不会生成替代人物回复。
- 官方人物聊天记录、稳定 ID 和输入草稿继续按现有规则保留。学习执行服务也未接入，学习入口不能声明已经开始教学、评估或保存学习成果。

官方人物聊天与目录同步尚未接入。自定义模型凭据、账号登录和官方人物消息是三条独立链路。

## 当前桌面账号

登录从账号菜单进入独立的 `#login`，沿用 BoardUI Auth Card。已有密码的账号走 `/api/app/auth/password/login`；短信验证码通过 `/api/app/auth/mobile/code` 获取，验证走 `/api/app/auth/mobile/login`，首次验证手机号时由 Java 创建账号。直接密码注册被 Java 拒绝，桌面端的注册页因此使用短信验证。NekoBuddy 扫码使用下文的 device/start 与 device/poll，只有收到有效的真实二维码内容才渲染。返回、过期、手机取消与消费后停止轮询；用户可重新获取。

`src-tauri/src/account_auth.rs` 在本机桌面主窗口运行账号请求。本机 release 使用 `npm run desktop:build:local` 连接 Java 服务 `http://127.0.0.1:8080`。部署者可设置 `NEKOPAPA_ACCOUNT_API_URL` 为受信任的 Java 服务基础地址，可在构建时配置或从启动进程环境读取。需要 HTTPS，本地联调可用回环 HTTP。账号 HTTP 请求拒绝跳转，服务端 Token 只保留在原生进程内；收到登录凭据后以授权请求读取 profile，只交给界面身份 ID、昵称、头像地址、NekoID、套餐和云点余额。退出时调用服务端 logout。会话在退出应用后丢弃，WebView 重载可读取当前进程的状态。浏览器预览和未配置服务的桌面版只展示真实的不可用状态。

本轮未验证部署地址、短信送达、手机端扫码或桌面端版本门禁，也未修改 Java 后端。下节的源码核查为历史记录。

更换头像走已认证的 `POST /api/app/user/profile/avatar`。桌面宿主用当前会话上传经过本机裁切的图片，表单字段为 `file`，核对 Java 回执的用户身份后更新会话中的头像地址；其他账号字段继续使用同一份会话资料。本机 Java 的 `NEKO_UPLOAD_ROOT` 需要为可写目录，`/profile/avatar/` 从该目录提供图片。

### 小屋账号模型

桌面小屋从独立登录页返回后，原生宿主请求 `GET /api/app/companion/current`，检查 `isCurrent` 与服务端身份。打开「同伴」时请求 `GET /api/app/companion/roster`，仅向界面提供归属当前账号的有效同伴的名称、身份键、等级、默契和可预览状态。预览仅限名册中满足 `canSwitch` 的同伴，并在准备模型前后复核。预览不修改账号当前同伴。官方模型按返回的 `companionRef` 和可用的 `modelResourceId` 向 `/api/app/companion/live2d/download-url` 领取签名清单。素材同伴使用当前资源包的 ID、对象键、大小和摘要向 `/api/app/companion/resources/download-urls` 申请签名，并核对回执。OSS 请求只携带服务端签发的地址。

本机 macOS release 包使用 `npm run desktop:build:local`。该命令注入本地服务地址、构建序号及 `dev` 渠道。Java 对设置了最低应用版本的模型按完整客户端信息判断可用性。小屋会区分当前同伴查询失败、模型暂未开放和签名请求失败。

宿主检查包体大小和 SHA-256，再按清单匹配 ZIP 内的模型入口。官方发布包的安装路径可以带 `live2d/`，其 ZIP 内部会按发布器规则省略这个目录。旧包使用清单的完整路径时也可加载。解包前将 Windows 路径分隔符转换为斜线，继续拒绝目录穿越、绝对路径和重复文件。宿主解包到本次登录的临时目录，复核正在加载的同伴身份后向主窗口提供模型资源句柄。相同账号会话内可复用当前和上一个已校验的模型包；登出或授权失效后句柄失效。小屋只渲染授权模型，失败可重试。浏览器预览可以检查登录入口和返回流程，真实账号授权与模型交付通过桌面宿主运行。

## Java 源码核查结果（2026-11-08，尚未接入）

已只读检查同工作区 `NekoBuddy-Bankend/Neko-Bankend` 的桌面认证、Token、资料、同伴名册和资源交付代码。未请求线上服务、读取私密配置或修改 Java / Rust。下面记录源码契约，不代表部署环境已验证。

- 桌面专用登录位于 `NekoAppDesktopAuthController`：`POST /api/app/auth/device/start` 返回二维码内容、会话标识、过期秒数和轮询间隔；`POST /api/app/auth/device/poll` 在手机确认并成功发布登录态时返回 `data.login.token`。关闭桌面登录面板应停止轮询；手机取消、二维码过期、已消费状态分别处理，不能把 `CONSUMED` 当成新登录回执。邮箱验证码登录另有接口，但默认关闭。
- 认证使用 `Authorization: Bearer …`。后端通过 Redis 会话滑动续期，未查到独立刷新 Token 接口；401 需要恢复未登录状态。客户端尚无真实会话存储，需实现原生凭据管理，不能沿用本机资料存储充当登录态。业务响应必须同时检查 HTTP 状态及 `{code,msg,data}` 中的 `code`。
- `GET /api/app/user/profile` 的 `data` 直接是用户资料和会员、云点信息；登录回执中的 `userAsset` 仅包含猫币、食物和零食，不能代替云点余额或推算月额度。
- `GET /api/app/companion/roster` 提供人物名册与当前同伴。联系人聊天选择不应调用 `POST /api/app/companion/current`，后者会修改账号常驻人物。名册当前还含 `promptText`，接入前需明确只同步公开资料的契约，不能将整份响应保存为联系人或允许覆盖官方设定。
- 五位本地人物 ID 与 Java ID 不可直接等同。历史迁移依据为 `lumia → cat_001 / model_lumia`、`rinne → cat_002 / model_nyx`、`iori → cat_003 / model_aria`、`shiori → cat_004 / model_lyra`、`tsumugi → cat_005 / model_kana`；实际身份和资源仍以服务端名册为准，不改已有本地联系人或聊天 ID。
- Live2D 已有 `GET /api/app/companion/live2d/download-url?companionRef=&modelId=`，返回版本、修订、压缩包大小和 SHA256、安装根目录、模型入口与临时下载地址。接口仍受发布、授权审核、版本、渠道和灰度门禁限制，不能假定五位人物全部开放。客户端中的 `public/live2d` 模型资源已移除，不再随构建打包；后续须在服务端确认人物可用后按需下载、校验并原子放入缓存，任何未开放、缺失或下载失败状态均显示头像。按需下载与缓存尚未实施。
- `ClientMetadataParser` 当前只接受移动端平台与 `arkui/flutter`，尚不识别 `macos/tauri`。需扩展真实桌面元数据契约，不能伪装成手机绕过发布门禁。
- 当前只能确认源码默认本地端口 8080，尚未确认可用的后端部署地址。模型供应商网关不能用作本产品账号服务地址。

账号入口应围绕登录与账号资料组织：未登录直接提供登录，登录后显示服务端昵称、头像及账号操作；模型、工具、外观和备份的快捷入口仍打开同一设置页；移除重复账号状态和指向错误的聊天记录项。

## 后续接 Java 时的实现范围

在上述已有接口基础上补齐桌面兼容与公开资料契约，再实施适配。以下是职责要求，不代表已完成接入：

1. **服务端选定人设。** 桌面端传稳定人物 ID、会话 ID、所选模式与用户消息。Java 根据已认证用户和人物 ID 读取正式提示词，执行身份、模式及权限校验，并在服务端组装请求。禁止接受客户端提供的官方 `prompt`、`system`、角色简介或标签作为人设覆盖。
2. **只同步公开目录。** Java 返回用于展示的人物资料、外观资源引用、目录版本和能力状态。桌面端按已有 ID 更新资料，不重建联系人或聊天 ID。人物提示词正文不进入前端包、本机配置、导入导出、聊天记录或同步响应。
3. **分开能力状态。** Java 人物服务可用后才启用陪伴聊天；学习模式需要 Java 学习编排及其依赖服务同时就绪。接通通用模型或下载 Live2D 资源不能代替这两项状态检查。
4. **可恢复的执行。** 复用同一会话 ID；请求包含可去重的消息 ID。连接失败保留草稿和已完成消息，取消需中止 Java 上游执行。重试不能重复计费、发送同一用户消息或覆盖其他入口的记录。版本不兼容或人物下架时给出明确状态，保留历史。
5. **明确版本。** Java 内部记录本轮实际使用的人设版本，便于审计和问题定位。桌面端可读取不含提示词内容的版本与能力信息；目录缓存失败不能悄悄回退为本地人设。展示用缓存与服务端执行权限各自校验。

## 接入验收

完成 Java 适配时，应以实际接口验证：五位人物均按固定 ID 命中正确人设；修改客户端姓名、简介、标签、外观或历史 `system` 消息无法替换人设；自建联系人的专业提示词仍生效；官方人物不能建群；断线、停止、重试和多个聊天入口保持同一会话记录；提示词正文没有出现在浏览器响应、本机存储或导出文件中。学习能力需独立完成资料、执行结果和失败恢复的验收。
